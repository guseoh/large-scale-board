# Large-Board 학습 프로젝트 인수인계

> 현행 규칙: 2026-11-21. 실제 설계·실험 이력은 [README](../README.md), [ROADMAP](ROADMAP.md), 프로젝트 [GitHub Wiki](https://github.com/guseoh/large-scale-board/wiki)에 보존합니다.

## 현재 우선순위: Spring REST API 기본기

목표는 **단순한 Article REST API를 직접 작성하고, HTTP 요청부터 DB 저장·응답까지의 동작을 설명할 수 있는 상태**입니다. 대용량/분산 실험은 이 기초가 안정된 뒤 진행합니다.

```text
S01 현재 Spring 환경 확인(필요한 만큼만)
→ S02 Article Controller·HTTP 메서드·상태 코드
→ S03 Request/Response DTO·기본 Validation
→ S04 JPA Entity·Repository·MySQL 저장/조회
→ S05 수정·삭제·트랜잭션·목록·페이징
→ S07 필요한 비즈니스 예외·Spring 기본 오류 처리
→ S08 컨트롤러·저장·요청 흐름 테스트
→ S06 회원/인증은 실제 사용 사례가 필요해지는 시점
→ 기본 게시판 사용·검증 이후 기존 Phase 0~13의 문제/실험 확장
```

기존 S01~S08의 **식별자를 유지하되 인증(S06)은 필수 선행 단계로 강제하지 않습니다.** Java 객체·제네릭·컬렉션 등이 막히면 J01~J05의 Pure Java 과제를 선택적으로 복습합니다. 기존 Phase 0~13의 세부 목차, 측정·완료 기준은 변경하지 않습니다. 이전 Phase 0의 측정·장애 훈련과 1단계 일부는 이미 근거가 있으므로 기초 API 완성을 위해 재작업하지 않습니다.

## 초반 구현을 작게 유지하는 규칙

- Article 한 기능의 **Controller → Service → Repository → DB** 흐름부터 구현합니다. 소규모에 맞는 DTO·엔티티·검증·트랜잭션을 사용하고, 인터페이스·추상화·계층을 무조건 추가하지 않습니다.
- 처음부터 Snowflake/`Persistable`/`BaseEntity`에 Article을 의존시키지 않습니다. 우선 Spring Data JPA의 기본 ID 전략과 SQL을 직접 확인합니다. 기존 라이브러리와 실험 데이터는 삭제하지 않습니다.
- 예외 처리는 필요한 비즈니스 오류와 입력 검증부터 시작하고, Spring MVC가 이미 제공하는 기본 처리를 재사용합니다. 모든 오류의 근본 원인 탐색, 불필요한 null 검증, 광범위한 400 세분화, 전역 엄격 JSON 설정은 명확한 계약/문제 없이 만들지 않습니다.
- **기본 안전은 유지합니다:** 올바른 요청 검증, DB 무결성 제약, 적절한 트랜잭션 경계, 필요한 인증·인가, 민감 정보 비노출, 오류 시 정상 성공을 가장하지 않기.
- Snowflake/대량 적재/Prometheus·Grafana/모니터링/장애 훈련/샤딩/CQRS는 고급 학습 자산입니다. 구현 필요를 실험으로 확인하거나 해당 실험을 학습 목표로 선택했을 때만 적용합니다.
- 초기 설계는 현재 요청·응답·상태·테이블 정도만 정의합니다. 거대한 ERD, 미래 도메인 설계, 분산 구조, 완성형 비기능 명세를 기초 CRUD의 진입 조건으로 두지 않습니다.

## AI와 사용자의 역할

- **사용자가 애플리케이션 `src/main` 코드를 직접 작성**합니다. AI는 요청한 완성 코드(파일 경로 포함)를 제공하고 코드 블록 바로 아래에 필요한 핵심 설명을 붙입니다. 테스트·측정 스크립트 작성은 AI가 지원할 수 있습니다.
- AI는 **명시적 요청 없이 `src/main`을 수정하지 않습니다**. 이번 문서 변경으로 현재 코드에 새 구조를 일괄 적용하지 않습니다.
- 한 묶음 진행 중 해당 부분의 테스트를 중심으로 확인하고, 묶음 완료 때 전체 테스트를 한 번 검증합니다. 테스트 성공/학습 완료/운영 적용은 각각 구분합니다.
- 긴 이론 설명이나 자동 퀴즈, 별도 과제, Obsidian 문서 제작을 기본 의무로 만들지 않습니다. 사용자가 질문한 개념만 필요한 만큼 깊게 다룹니다.

## 고급 단계 진입 기준

기초 REST API에서 실제 요청을 보내 게시글 생성/조회/수정/삭제, 검증 실패, JPA 저장 동작, 트랜잭션과 페이징, 필요한 오류 응답을 **테스트나 실행 증거로 확인**했을 때 고급 단계로 넘어갑니다.

그 후 `현재 구조 → 문제 재현 → 측정 기준선 → 원인 가설 → 대안과 Trade-off → 사용자 선택 → 직접 구현 → 재측정/장애 실험` 순서로 진행합니다. 새로운 인프라를 미리 도입하지 않습니다. Phase 완료는 [ROADMAP](ROADMAP.md)의 각 실험 완료 조건으로 판단합니다.

## 기존 구현과 Git·Wiki의 경계

- 현재 `main`에는 Snowflake, `Member`, `BaseEntity`, 로깅, 오류 처리, DB 환경, `datagen`, 메트릭과 실험 테스트가 있습니다. **Article CRUD는 아직 main에서 확인되지 않습니다.**
- 2026-11-19 확인된 `main` CI 성공과 1-A/1-B-3 실험 기록은 기초 API 완료의 증거가 아닙니다. `phase/1b-signup`의 미완성 브랜치와 기존 Wiki 인수인계는 과거/별도 작업의 근거로 보존합니다.
- 기존 환경(Windows·IntelliJ·PowerShell, Java 21, Spring Boot 4.1.0, Gradle 9.5.1, MySQL 8.4)을 유지합니다. 테스트에 Docker가 필요하며 개발 DB의 `ddl-auto=create`는 데이터를 초기화할 수 있습니다.
- 일반 개발 커밋·푸시는 사용자가 수행합니다. 명시적으로 요청한 Git 문서 작업은 별도 브랜치·PR로 검증해 처리할 수 있습니다. 중요한 실험은 해당 프로젝트 GitHub Wiki에, 공통 장기 기억은 `guseoh/cs/Wiki`에 근거와 상태를 분리해 기록합니다.
- 새 세션에서는 최신 `main`, 열린 브랜치/PR/Issue, README, 이 문서 및 관련 실험 문서를 확인합니다. **다음은 S01 간단 점검 후 S02 Article Controller**입니다. 사용자 지시 없는 기존 기능 삭제/리팩터링은 금지합니다.
