# [0단계] [장애 훈련] MySQL 중단 시 앱의 동작과 탐지

> 상태: **초안**. GitHub Issue 본문으로 옮길 것. 훈련일 2026-11-12, `phase/0-foundation` (E 묶음, 미커밋 상태).
> 도구: `scripts/drill-mysql.ps1`, `loadtest/scenarios/drill-mysql.js`, 알림 규칙 `infra/prometheus/rules/board-alerts.yml`.

## 실험 전

- **문제:** MySQL이 멈추면 앱은 어떻게 실패하고, 그것을 무엇으로 몇 초 만에 알 수 있는가. DB와 무관한 API까지 번지는가.
- **가설 (설계 13절의 예측)**
  - `/ping`은 영향을 받지 않는다.
  - `/ping/db`는 HikariCP 기본 `connection-timeout`(30초) 동안 기다린 뒤 실패한다. 그동안 Tomcat 스레드가 쌓여 200개에 닿으면 `/ping`까지 느려진다.
  - 대시보드에서는 `mysql_up` 0 → HikariCP 대기 증가 → 사용 중 스레드 증가 → p99 급증 → 5xx 증가 순으로 보인다.
- **바꾸는 변수:** 회차마다 타임아웃 설정(아래 표). 주입 방식 3가지는 회차마다 같다.
- **부하:** k6 도착률 고정. `/ping`과 `/ping/db`에 각각 초당 100건. 정상 60초 → 장애 60초 → 복구 후 120초.
- **주입:** `docker compose stop mysql`(정상 종료), `kill`(강제 종료), `pause`(응답 없음).
- **데이터셋:** ds-v0 (비즈니스 테이블 없음. `SELECT 1`만 쓴다).

| 회차 | HikariCP `connection-timeout` | JDBC `connectTimeout` / `socketTimeout` | 관리 포트 |
| --- | --- | --- | --- |
| 1 기본 | 30초 (기본값) | 없음 | 요청 포트와 같음 (8081) |
| 2 | 3초 (설계안) | 없음 | **분리 (8082)** |
| 3 최종 | **1초** | 3초 / 10초 | 분리 (8082) |

> 2회차에 관리 포트 분리와 타임아웃 변경을 함께 넣었다. 관리 포트 분리는 요청 경로가 아니라 지표 수집 경로만
> 바꾸므로 요청 처리 결과의 비교를 흐리지 않는다고 판단했다.

### 결과: 회복

| 항목 | 1 기본 | 3 최종 |
| --- | --- | --- |
| MySQL이 다시 연결을 받기까지(복구 명령 후) | stop 3.7초, kill 4.9초, pause 0.8초 | stop 5.1초, kill 2.1초, pause 0.4초 |
| `/ping/db`가 초당 95건 이상 처리(복구 명령 후) | 13~15초 | 16~17초 |
| 알림이 꺼지기까지(복구 명령 후) | MySQLDown 1~9초 | MySQLDown 2~8초, HikariTimeout 62~68초, HighErrorRate 48~58초 |

- 정상화 시간은 15초 창으로 계산한 처리율이라 실제보다 최대 15초 늦게 나온다. 회차 간 비교에만 쓴다.
- HikariTimeout과 HighErrorRate는 1분 창으로 계산하므로 복구 후 약 1분 동안 켜져 있다.

### 해석

1. **가설의 앞부분은 틀렸고 뒷부분은 맞았다.** `/ping`은 영향을 받았다. 기본 설정에서 `/ping`은 87%를 처리하지 못했다. 원인은 예측대로 Tomcat 스레드 고갈이다.
2. **리틀의 법칙으로 정확히 설명된다.** 동시에 떠 있는 요청 수 = 초당 요청 × 기다리는 시간이다.
   - 30초: 100 × 30 = 3,000 ≫ 200 → 스레드 전부 고갈
   - 3초: 100 × 3 = 300 > 200 → 여전히 고갈(`/ping` 12% 손실)
   - 1초: 100 × 1 = 100 < 200 → 여유. 실측 최대 104개

   **커넥션 대기 시간의 상한은 "Tomcat 스레드 수 ÷ 그 API의 초당 요청 수"보다 작아야 한다.** 설계안 3초는 초당 100건에서 이미 부족했다.
3. **가장 큰 발견은 관측 사각지대다.** 지표 엔드포인트(`/actuator/prometheus`)가 요청과 같은 Tomcat 스레드 풀을 써서, 스레드가 고갈되자 지표 수집이 실패했다. 그 결과 다음 일이 생겼다.
   - 정작 원인을 가리키는 커넥션 풀 알림(HikariTimeout, HikariPending)과 5xx 알림이 켜지지 않았다.
   - 앱은 살아 있는데 `AppDown`이 켜져 원인을 잘못 가리켰다.
   - 관리 포트를 분리(8082)하자 지표가 끊기지 않았고, HikariTimeout이 **5~8초** 만에 켜져 가장 빠른 탐지 수단이 됐다.
4. **pause(응답 없음)는 소켓 타임아웃이 없으면 끝나지 않는다.** 이미 쿼리를 보낸 커넥션 10개가 MySQL을 재개할 때까지 매달렸다(60초). `socketTimeout=10000`을 넣자 정확히 10초에 끊겼다.
5. **대시보드 순서 예측은 부분적으로 맞았다.** 지표가 보이는 3회차 기준으로 HikariTimeout(5~8초) → MySQLDown(20~23초) → HikariPending(33~35초) → HighErrorRate(70~73초) 순이다. 탐지 시간은 대부분 각 규칙의 유지 시간(`for`)과 계산 창이 정한다.

### 비용

- **`connection-timeout` 1초:** 풀이 잠깐 모자란 순간(트래픽 폭증)에도 1초 만에 503을 준다. 기다리면 성공했을 요청까지 실패한다. 2단계 "느린 쿼리로 커넥션 풀 고갈" 훈련에서 이 비용을 직접 잰다.
- **`socketTimeout` 10초:** 10초보다 오래 걸리는 정상 쿼리도 끊는다. 느린 쿼리를 일부러 재는 실험(H-03 등)에서는 값을 늘리고 실험 조건에 적는다. 쿼리별 타임아웃(JPA query timeout)이 더 정밀한 대안이다.
- **관리 포트 분리:** 포트가 하나 늘고, 테스트에서는 같은 포트로 되돌리는 설정이 필요하다. 4단계에서 앱을 컨테이너로 옮길 때 포트를 둘 다 열어야 한다.

### 결론

- 확정한 설정: `connection-timeout=1000`, `validation-timeout=750`, `connectTimeout=3000`, `socketTimeout=10000`, `management.server.port=8082`.
- 커넥션 대기 시간은 처리량과 스레드 수로 계산해 정한다. 처리량이 늘면 다시 계산한다.
- 1차 탐지 신호는 HikariTimeout, 원인 확인은 MySQLDown이다.

### 고정한 테스트

- `GlobalExceptionHandlerTest`: DB 커넥션 획득 실패 → 503 `DB_UNAVAILABLE`, 내부 메시지 미노출(A 묶음에서 작성).
- `PrometheusEndpointTest`: 알림 규칙이 쓰는 HikariCP 지표가 노출되는지.
- 장애 주입 자체는 자동 테스트로 만들지 않았다. `scripts/drill-mysql.ps1`로 다시 실행한다.

### AI 활용

- 훈련 도구, 분석, 설정 변경은 Claude가 작성하고 실행했다(0단계 작업 방식).
- 설계안 3초를 그대로 확정하지 않고, 리틀의 법칙으로 3초가 부족하다고 예측한 뒤 2회차에서 확인했다.
