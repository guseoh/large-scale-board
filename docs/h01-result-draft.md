# [0단계] [비교 실험] 100만 건 적재 방식 비교 (JPA saveAll, JDBC 배치, LOAD DATA)

> 상태: **초안**. GitHub Issue 본문으로 옮길 것. 측정일 2026-11-11~12, 커밋 `4ed0b39` 위의 작업 트리(D 묶음, 미커밋 상태)에서 측정.

## 실험 전

- **문제:** 2~4단계에서 수천만 건을 적재해야 한다. 어떤 방식으로 넣어야 하고, JPA로 대량 INSERT를 할 때 무엇을 설정해야 하는가.
- **가설(H-01):** 배치 설정 없이 JPA로 100만 건을 넣으면 JDBC 배치보다 10배 이상 느리다.
- **바꾸는 변수:** 적재 방식 하나. 묶음 크기 1,000, 묶음마다 트랜잭션 1개(커밋 = flush·clear), 같은 시드의 같은 행.

| 방식 | 내용 |
| --- | --- |
| A | JPA `saveAll`, 배치 설정 없음, 엔티티가 `Persistable` 구현 |
| A' | A에서 `Persistable` 미구현 (ID를 직접 넣음) |
| B | A + `hibernate.jdbc.batch_size=1000` + `rewriteBatchedStatements=true` |
| B' | B에서 ID 전략만 `IDENTITY` (AUTO_INCREMENT 테이블) |
| C | `JdbcTemplate.batchUpdate` + `rewriteBatchedStatements=true` |
| D | CSV 생성 후 `LOAD DATA INFILE` (서버가 마운트된 폴더에서 읽음) |

- **데이터셋:** `exp_load_article`(PK `BIGINT` Snowflake, 보조 인덱스 없음). 행당 평균 약 760바이트(CSV 기준), 100만 건 CSV 759MB. 시드 `20261111`.
- **환경:** MySQL 8.4.11(CPU 2코어, 버퍼 풀 512MB, 바이너리 로그 켜짐, `sync_binlog=1`, `innodb_flush_log_at_trx_commit=1`). datagen은 호스트 JVM(Temurin 21)에서 실행.
- **중단 조건:** 한 번이 30분을 넘으면 멈추고 10만 건 결과로 환산. A' 예상치가 40분이 넘어, 느린 방식(A, A', B')은 처음부터 10만 건으로 측정해 환산했다.

- SELECT 27~28건은 datagen 기동과 `COUNT(*)` 확인이다. B·C의 1,000건 추가분은 아래 "예상과 다른 점"에 있다.
- 같은 시드로 만든 100만 건 CSV는 4번 모두 SHA-256이 같았다(`08b4ffb9…`).

### 해석

**가설은 맞았다.** A(약 1,244초) ÷ C(91.1초) = **약 13.7배**. 배치 설정 하나로 JPA(B)는 C와 10% 차이까지 따라온다.

1. **행당 비용 = DB 왕복 횟수.**
   - A는 행 하나에 약 1.24ms였다. 기준선 측정에서 잰 DB 왕복 한 번(약 0.9ms)에 Hibernate 처리 비용을 더한 값과 맞다.
   - A'는 약 2.34ms로 거의 두 배다. `merge`가 INSERT 전에 SELECT를 한 번 더 보내서 왕복이 두 번이다. 실제로 SELECT가 정확히 10만 건 더 나갔다.
   - B·C는 `rewriteBatchedStatements`로 INSERT 1,000건을 문장 1개로 묶어, 100만 건을 왕복 1,000번으로 끝낸다.
2. **`Persistable`(A와 A'의 차이):** ID를 애플리케이션이 넣는 이상 `isNew()`를 구현하지 않으면 모든 저장이 SELECT + INSERT가 된다. 적재 속도가 절반이 된다. → 1단계 엔티티 공통 상위 클래스에서 `Persistable`을 구현한다(D0-12 확인).
3. **IDENTITY는 배치를 끈다(B').** 배치 설정이 켜져 있어도 INSERT가 행마다 1건씩 나갔다(10만 건 → 10만 문장). INSERT를 실행해야 ID를 알 수 있어서, Hibernate가 영속화하는 순간 바로 INSERT를 보내기 때문이다. Snowflake처럼 애플리케이션이 ID를 만드는 방식의 장점이 여기서 드러난다.
4. **JPA 배치(B)와 JDBC 배치(C)의 차이는 약 10%다.** 나가는 문장 수는 같다(INSERT 1,000). 차이는 엔티티 생성과 영속성 컨텍스트 처리 같은 클라이언트 쪽 비용이다. MySQL CPU도 B가 더 낮아(28% 대 40%) 병목이 앱 쪽임을 보여준다.
5. **LOAD DATA(D)는 C보다 1.4배 빠른 데 그쳤다.** CSV 생성(21초)까지 넣으면 C와 비슷하다. 또 3회 편차가 크다(50~70초). 원인 후보는 다음과 같고, 검증하지 않았다.
   - CSV를 Windows 폴더에서 Docker Desktop 파일 공유로 읽는 경로가 느리다.
   - 100만 건을 트랜잭션 하나로 넣어서, 바이너리 로그와 redo 로그를 한꺼번에 많이 쓴다.
   - MySQL CPU 2코어 제한.

### 예상과 다른 점

- **B'(IDENTITY)가 A보다도 느렸다** (행당 1.81ms 대 1.24ms). 둘 다 행마다 INSERT 1건인데 차이가 난다. 후보는 생성된 키를 돌려받는 처리(`getGeneratedKeys`)와 AUTO_INCREMENT 락이다. 검증하지 않았다.
- **배치 프로필(B, C)에서 트랜잭션마다 SELECT가 1건씩 더 나갔다.** 5,000건(트랜잭션 5개)으로 재현해 문장 통계(`performance_schema` digest)를 보니 다음 문장들이 함께 나갔다.

  | 문장 | 횟수 | 보내는 쪽 |
  | --- | --- | --- |
  | `SET autocommit = ?` | 20 | 트랜잭션 시작·끝 (Spring) |
  | `SELECT @@session.transaction_read_only` | 17 | MySQL 드라이버 |
  | `SET character_set_results = ?` | 10 | MySQL 드라이버 |
  | `INSERT ...` | 5 | 데이터 |
  | `COMMIT` | 5 | |

  묶음 적재에서는 무시할 만하지만, 요청 하나가 행 하나를 쓰는 API에서는 이 부수 왕복이 각각 약 0.9ms씩 더해진다. 드라이버 옵션(`useLocalSessionState` 등)으로 줄일 수 있는지는 1단계 이후 실험 후보다.

### 비용

- `Persistable` 구현: 엔티티마다 새 엔티티 여부 플래그와 콜백(`@PostPersist`, `@PostLoad`)이 필요하다. 공통 상위 클래스로 한 번만 만든다.
- `rewriteBatchedStatements=true`: INSERT가 합쳐지므로 SQL 로그와 문장 통계에서 개별 행이 보이지 않는다. 합친 문장이 `max_allowed_packet`(기본 64MB)을 넘으면 드라이버가 나눠 보낸다.
- `LOAD DATA INFILE`: 접속 계정에 서버 전체 권한인 `FILE`이 필요하고, 파일이 `secure_file_priv` 폴더 안에 있어야 한다. 엔티티 규칙(검증, 이벤트)을 전혀 거치지 않는다.

### 결론

- **대량 적재(datagen):** `LOAD DATA`를 기본으로 쓴다. CSV가 중간 산출물로 남아 재적재와 결정성 검증에도 쓰인다. 수천만 건 규모에서 C와의 차이가 커지는지는 2단계(게시글 1,000만 건)에서 다시 본다.
- **애플리케이션 코드에서 여러 건을 저장할 때:** JPA라면 `batch_size`와 `rewriteBatchedStatements`를 켜고, `Persistable`을 구현하고, IDENTITY를 쓰지 않는다. 그러면 JDBC 직접 사용과 10% 차이다.
- **IDENTITY 전략은 쓰지 않는다.** Snowflake를 애플리케이션에서 할당하는 결정(D0-12)을 유지한다.

### 함께 발견하고 고친 것

- **시간대:** `hibernate.jdbc.time_zone=UTC`가 있으면 Hibernate는 `LocalDateTime`을 JVM 기본 시간대(KST)의 시각으로 보고 UTC로 바꿔 저장한다. 그래서 JPA로 넣은 값만 9시간 앞당겨졌다(CSV·JDBC와 불일치). datagen은 JVM 기본 시간대를 UTC로 고정해 해결했다. **앱에도 같은 설정이 있으므로 1단계 첫 엔티티에서 같은 문제가 생긴다.** JVM 시간대를 UTC로 고정할지, 시각 타입을 `Instant`로 쓸지 1단계에서 정한다.
- **생성 기간:** 설계는 "기준 시각에서 과거 365일"이지만, Snowflake 기준 시각(2026-01-01) 이전은 ID로 표현할 수 없다. 기준 시각 2026-11-01에서 과거 300일로 줄였다. 범위를 벗어나면 생성기가 시작부터 오류를 낸다.
- **바이너리 로그:** H-01을 반복하는 동안 바이너리 로그가 7.8GB 쌓여 볼륨이 8.8GB가 됐다(데이터는 0.8GB). 보관 스크립트가 보관 전에 로그를 정리하도록 고쳤다. 정리 후 보관본은 201MB다.
