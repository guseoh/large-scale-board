## 3. 계단식 측정 (최대 처리량 찾기)

계단마다 5초 동안 올리고 30초 유지했다. 표의 값은 유지 구간(첫 5초 제외)의 값이다.

### `/ping` (testid `ping-step-1`)

| 목표 | 서버 처리 | 서버 평균 | k6 CPU (한도 200%) | k6가 버린 요청/초 | 앱 CPU (호스트 대비) |
| --- | --- | --- | --- | --- | --- |
| 1,000 | 1,005 | 0.2ms | 50% | 0 | 4.6% |
| 2,000 | 1,951 | 0.2ms | 87% | 65 | 7.7% |
| 3,000 | 3,003 | 0.2ms | 95% | 0 | 10.2% |
| 4,000 | 3,988 | 0.2ms | 115% | 29 | 13.0% |
| 5,000 | 4,952 | 0.2ms | 143% | 47 | 15.6% |
| 6,000 | 5,990 | 0.2ms | 190% | 5 | 18.3% |
| 7,000 | 6,556 | 0.2ms | **197%** | **494** | 22.0% |
| 8,000 | 5,729 | 0.2ms | 126% | **2,210** | 19.2% |

- 서버 처리 시간은 끝까지 평균 0.2ms, p99 1ms 이하로 변하지 않았다. Tomcat 사용 중 스레드는 최대 7개.
- 초당 7,000건에서 k6 CPU가 한도에 닿았고, 이후 요청을 보내지 못하고 버렸다. **측정한 한계는 앱이 아니라 측정 장비의 한계다.**

### `/ping/db` (testid `pingdb-step-1`)

| 목표 | 서버 처리 | 서버 평균 | 서버 p99 | 풀 사용 / 대기 | Tomcat 사용 중 | 커넥션 획득 평균 | MySQL CPU | 호스트 CPU |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1,000 | 1,110 | 1.0ms | 1.9ms | 2 / 0 | 3 | 0ms | 15% | 50% |
| 2,000 | 2,101 | 1.0ms | 2.6ms | 4 / 0 | 6 | 0ms | 24% | 54% |
| 3,000 | 2,968 | 6.7ms | 92.9ms | **10 / 27** | 25 | 4.3ms | 42% | 76% |
| 4,000 | 3,660 | 39.7ms | 236.9ms | 10 / **189** | **200** | 37.1ms | 63% | 95% |
| 5,000 | **4,186** | 44.7ms | 198.2ms | 10 / 189 | 200 | 42.3ms | 69% | 97% |
| 6,000 | 3,986 | 45.8ms | 202.4ms | 10 / 189 | 200 | 43.3ms | 68% | 97% |
| 7,000 | 2,774 | 49.5ms | 246.4ms | 10 / 189 | 200 | 46.7ms | 44% | 85% |

- MySQL CPU %는 코어 1개 기준이다(한도 200%). 최대 69%이므로 MySQL은 포화되지 않았다. 실행 중 스레드도 최대 7개.
- 초당 4,000건부터 Tomcat 스레드 200개가 모두 차 있고, 그중 189개가 커넥션을 기다린다(200 − 사용 중 10 − 1).
- 서버 평균의 증가분(1ms → 45ms)은 거의 전부 **커넥션을 얻으려고 기다린 시간**이다(획득 평균 37~47ms).
- 6,000·7,000건 구간은 앱·k6·Docker VM이 함께 호스트 CPU를 다 써서(85~97%) 결과를 믿기 어렵다. 최대 처리량은 5,000건 구간의 4,186건으로 잡는다.

## 4. 표준 측정 (초당 2,000건, 워밍업 1분 + 3분 × 3회)

두 API를 풀이 차기 전인 같은 도착률로 맞춰 "DB 왕복 한 번의 비용"을 비교했다. 값은 각 3분 구간에서 시작 10초와 끝 5초를 뺀 값이다.

| 지표 | `/ping` r1 / r2 / r3 | **중앙값** | `/ping/db` r1 / r2 / r3 | **중앙값** |
| --- | --- | --- | --- | --- |
| 서버 평균 | 0.19 / 0.16 / 0.21ms | **0.19ms** | 1.07 / 1.07 / 1.22ms | **1.07ms** |
| 서버 p99 | 1ms 이하 (3회 모두) | 1ms 이하 | 3.08 / 2.95 / 4.97ms | **3.08ms** |
| k6 p50 | 1.15 / 1.06 / 1.38ms | 1.15ms | 1.89 / 1.94 / 2.01ms | 1.94ms |
| k6 p99 | 13.1 / 24.7 / 39.4ms | 24.7ms | 20.1 / 7.0 / 37.4ms | 20.1ms |
| 실패율 | 0.10 / 0.04 / 0.05% | 0.05% | 0.03 / 0.03 / 0.05% | 0.03% |
| 풀 사용 최대 | 0 | | 4 / 4 / 4 (대기 0) | |
| 앱 CPU (호스트 대비) | 7.0 / 6.6 / 7.0% | | 9.3 / 9.8 / 9.9% | |
| MySQL CPU (코어 1개 기준) | 약 2% | | 19.7 / 23.2 / 22.0% | |

- **서버 평균은 3회 사이 편차가 ±10% 안**이다. k6 p99는 같은 조건에서 7~39ms로 흔들렸다.
- 실패는 모두 `dial: i/o timeout`(TCP 연결 실패)이다. 앱이 오류를 낸 것이 아니다.

## 5. 용량 계산

### DB 왕복 비용

- 서버 평균 차이: 1.07 − 0.19 = **0.88ms**. k6 p50 차이(1.94 − 1.15 = 0.79ms)와도 비슷하다.
- `SELECT 1`은 MySQL 안에서 거의 시간이 들지 않는다. MySQL CPU로 계산하면 쿼리 하나당 약 0.11ms(코어 1개의 22% ÷ 2,000건/초)다.
- 나머지 대부분은 **경로 비용**이다. 앱은 호스트에 있고 MySQL은 Docker Desktop VM 안에 있어서, 왕복마다 포트 포워딩(`localhost:3310`)을 거친다. 4단계에서 앱을 컨테이너로 옮기면 이 값이 바뀌므로 다시 잰다.

### 커넥션 풀의 상한 (리틀의 법칙)

리틀의 법칙: **동시에 쓰이는 커넥션 수 = 초당 요청 수 × 요청 하나가 커넥션을 쥐는 시간**.

- 검증: 초당 2,000건 × 약 1ms = 평균 2개. 실측 최대 4개와 맞는다.
- 이론 상한: 풀 10개 ÷ 1ms = **초당 10,000건**.
- 실측 상한: **초당 약 4,200건**. 실효 점유 시간 = 10 ÷ 4,200 ≈ **2.4ms**.
- 1ms가 2.4ms로 늘어난 이유는 **호스트 CPU 포화(95~97%)**로 본다. k6, 앱, Docker VM이 같은 12코어를 나눠 쓴다. 그래서 커넥션을 쥔 스레드가 CPU를 기다리고, 반납된 커넥션을 받을 대기 스레드가 깨어나는 데도 시간이 걸린다. 운영처럼 장비를 나누면 이 비용은 줄어든다.

### 이후 단계 API의 상한 추정

DB를 쓰는 API의 상한은 이 환경에서 대략 **풀 10 ÷ (쿼리 수 × 약 1ms + 쿼리 자체 비용)**이다.

| 요청 하나의 커넥션 점유 | 상한 (호스트 여유가 있을 때) | 상한 (호스트 포화 시, ×2.4 보정) |
| --- | --- | --- |
| 쿼리 1개, 비용 무시 | 10,000건/초 | 4,200건/초 |
| 쿼리 3개, 비용 무시 | 3,300건/초 | 약 1,400건/초 |
| 쿼리 1개 + 실행 5ms | 1,600건/초 | 측정 필요 |

### 다음 병목 추정 (측정하지 않음)

- **앱 CPU:** 요청 하나당 CPU가 `/ping` 약 0.4ms, `/ping/db` 약 0.6ms였다(호스트 12코어 × 사용률 ÷ 처리량). 이 비율이면 앱 혼자 12코어를 다 쓸 때 수만 건이지만, 실제로는 같은 장비의 k6·Docker VM과 CPU를 나눈다.
- **MySQL CPU:** `SELECT 1` 하나에 약 0.11ms이므로, 2코어 한도에서 초당 약 18,000건이다.
- 따라서 풀을 늘리면 다음 병목은 **호스트 CPU**(측정 장비와 앱이 같은 장비)일 가능성이 가장 크다.

## 6. 측정 도구에서 발견한 것 (앞으로의 측정 규칙)

1. **주 지표는 서버 히스토그램이다.** k6 p99는 같은 조건에서 7~39ms로 흔들렸다. 클라이언트와 서버 사이에 Docker Desktop 네트워크와 k6 CPU가 끼어 있기 때문이다. k6는 실패율과 버린 요청 수를 확인하는 데 쓴다.
2. **k6 한도는 초당 약 6,500건이다** (CPU 2코어). 이보다 높은 처리량을 재려면 k6 CPU 제한을 올려야 하는데, 그만큼 MySQL과 CPU를 다툰다. 2~5단계 API는 대부분 이 아래에서 꺾일 것이므로 지금은 유지한다. 모든 실행에서 k6 CPU와 `dropped_iterations`를 함께 확인한다.
3. **1ms 미만은 구분되지 않는다.**
   - 서버 히스토그램의 가장 작은 버킷이 1ms라 `/ping`의 p99가 "1ms 이하"로만 보인다. 필요하면 `management.metrics.distribution.minimum-expected-value.http.server.requests`로 더 작은 버킷을 만든다.
   - HikariCP의 커넥션 사용 시간 지표(`hikaricp_connections_usage_seconds`)는 ms 정수로 기록된다. 1ms 미만이 0으로 잘려서 평균이 0.19ms로 실제(약 1ms)보다 낮게 나온다. 커넥션 점유 시간은 서버 평균으로 추정한다.
4. **배경 부하가 크다.** 부하 전에도 호스트 CPU가 50~64%였다. 측정할 때는 IDE 인덱싱, 브라우저 등 다른 프로그램을 줄이고, 호스트 CPU를 측정 조건에 기록한다.
5. **TCP 연결 실패 0.03~0.14%가 바닥값이다.** Docker Desktop이 컨테이너에서 호스트로 연결을 넘기는 경로에서 생긴다. 실패율을 비교하는 실험에서는 이 값을 빼고 본다.
6. **Git Bash에서 k6를 실행할 때는 `MSYS_NO_PATHCONV=1`이 필요하다.** 없으면 `/scripts/...` 인자가 Windows 경로로 바뀌어 k6가 스크립트를 찾지 못한다. PowerShell에서는 문제없다.

## 7. 다음 단계의 출발점

- **2단계 장애 훈련 "느린 목록 쿼리로 커넥션 풀 고갈":** 풀이 차는 지점은 `SELECT 1` 기준 초당 약 3,000건이다. 쿼리가 느려지면 이 지점이 비례해서 내려온다(점유 5ms면 약 2,000건, 50ms면 약 200건).
- **풀 크기 변경 실험:** 풀을 늘리면 대기는 줄지만, 이 환경에서는 호스트 CPU가 먼저 포화될 가능성이 크다. 풀 크기만 바꾸는 비교 실험으로 확인한다.
- **`ping.js` 통과 기준:** 실패율 1% 미만에 더해 서버 p99 `/ping/db` 5ms 이하를 제안한다. 표준 측정 최대가 4.97ms였다.
